# FlowPay Backend - Users + Auth Module

## Goal

Implement the first usable `users` and `auth` backend slice:

- `POST /auth/register`
- `POST /auth/login`
- `GET /auth/me`

This slice creates users and auth credentials only. It intentionally does not create wallets, welcome bonus ledger entries, balances, or transfers.

## TL;DR

- Build a lightweight `users` + `auth` backend slice with register, login, and authenticated user lookup.
- Keep the implementation simple: no new domain entities with no behavior, no duplicated DTO files, no hand-written migration.
- Preserve architecture through import boundaries, ports, composition root, and architecture tests.
- Use PostgreSQL-backed integration tests for endpoint behavior and persistence.
- Keep `/auth/register` provisional: it returns `{ user }` only until `wallets` + `ledger` complete the public contract.

## Team TL;DR

**What we are building:** Users can register with username/password, log in, receive a JWT access token, and call `/auth/me`.

**What we are not building yet:** Wallet creation, welcome bonus, balance response, ledger writes, transfers, refresh tokens, recovery, MFA, or OAuth.

**Why this shape:** Auth is required before wallet and transfer work, but this slice should not pull in financial responsibilities. A light hexagonal structure keeps the module clean without generating empty domain classes.

## Design Principle

Use a light hexagonal structure for simple modules.

ADR 0001 requires dependency direction and ownership discipline; it does not require empty domain objects or one file per concept. For this slice, `users` and `auth` mostly coordinate persistence, password hashing, and token creation. They do not yet have rich domain behavior, so do not create domain entities that only mirror database rows.

Use:

- `application/` for use cases and public DTOs;
- `ports/` for repository contracts and adapter-neutral records/errors;
- `adapters/` for FastAPI, SQLAlchemy, passlib, python-jose;
- `flowpay/composition.py` for concrete cross-module wiring.

Create `domain/` files later only when a module has real domain invariants worth protecting.

## Contract Scope

`POST /auth/register` has a provisional response in this phase:

```json
{
  "user": {
    "id": "usr_123",
    "username": "alice"
  }
}
```

The public target contract in `docs/specs/04-api-contract.md` remains `user + wallet`, with wallet balance derived from the welcome bonus ledger entry. That full contract belongs to the later `wallets` + `ledger` implementation, not this auth slice.

## Architecture Constraints

Follow ADR 0001 and ADR 0005:

- Keep `users` and `auth` as separate modules.
- Keep application code independent from FastAPI, SQLAlchemy, passlib, and python-jose.
- `auth` may call the public `users.application.UserService`.
- `auth` must not import `users.adapters.*`, users ORM models, or users database tables.
- `auth` should receive `UserSummary` from `users.application`, not a users persistence record.
- Concrete cross-module adapter wiring belongs in `flowpay/composition.py`, not inside `auth`.
- Password hashing and verification stay inside `auth`.
- JWT access tokens use HS256, `AUTH_SECRET_KEY`, and payload fields only: `sub`, `iat`, `exp`.
- Access token expiry is 3600 seconds.
- Repositories use `flush()` but do not `commit()` or `rollback()`.
- The request DB session is the unit of work: `commit()` after successful request, `rollback()` on exception.

  ```python
  import flowpay.users.adapters.user_orm  # noqa: F401
  import flowpay.auth.adapters.credentials_orm  # noqa: F401
  ```

- The updated override shape:

  ```python
  def override_get_db():
      try:
          yield db
          db.commit()
      except Exception:
          db.rollback()
          raise
  ```

  Because the session uses `join_transaction_mode="create_savepoint"`, `db.commit()` releases
  to the savepoint instead of committing for real. The outer transaction rolls back after each test.
  Without this, integration tests that depend on committed state within the same request will fail.

## Module Details

### `users.application.user_service`

Define:

- `UserSummary`: public DTO with `id` and `username`.
- `UsernameAlreadyExistsError`.
- `UserService`.

Responsibilities:

- `create_user(username) -> UserSummary`
- `get_by_id(user_id) -> UserSummary | None`
- `get_by_username(username) -> UserSummary | None`
- Convert repository records to `UserSummary`.
- Translate `UsernameConflictError` to `UsernameAlreadyExistsError`.

This file is the public API other modules may call.

### `users.ports.user_repository`

Define:

- `UserRecord`: adapter-neutral persistence record with `id`, `username`, `created_at`.
- `UsernameConflictError`.
- `UserRepository` protocol.

Rationale:

- Avoids creating a domain entity with no behavior.
- Gives application code a stable record shape without importing SQLAlchemy.
- Gives adapters a non-SQLAlchemy error to raise on unique conflicts.

### `users.adapters`

`user_orm.py`

- SQLAlchemy model for `users`.
- Owns table mapping only.

`user_repository.py`

- Implements `UserRepository`.
- Uses `generate_id("usr_")`.
- Uses `flush()` after insert.
- Converts SQLAlchemy `IntegrityError` to `UsernameConflictError`.
- Never calls `commit()` or `rollback()`.

### `auth.application.auth_service`

Define:

- `InvalidCredentialsError`.
- `AuthService`.

Constructor dependencies:

- `CredentialsRepository`
- `UserService`
- `hash_fn`
- `verify_fn`

Responsibilities:

- `register(username, password) -> UserSummary`
  - create user through `UserService`;
  - hash password;
  - create credentials;
  - return `UserSummary`.
- `login(username, password) -> UserSummary`
  - resolve user through `UserService`;
  - load password hash through `CredentialsRepository`;
  - verify password;
  - return `UserSummary`.
- `get_by_id(user_id) -> UserSummary | None`

Constraints:

- Does not import FastAPI, SQLAlchemy, passlib, python-jose, or `users.adapters.*`.
- Does not return password hashes.

### `auth.ports.credentials_repository`

Define:

- `CredentialsRepository` protocol.

Keep it minimal:

- `create(user_id, password_hash) -> None`
- `get_password_hash(user_id) -> str | None`

Rationale:

- `AuthCredentials` has no behavior in this phase.
- Returning only the hash needed for verification keeps the application surface smaller.

### `auth.adapters`

`credentials_orm.py`

- SQLAlchemy model for `auth_credentials`.

`credentials_repository.py`

- Implements `CredentialsRepository`.
- Uses `flush()` after insert.
- Never calls `commit()` or `rollback()`.
- Sets both `created_at` and `updated_at` to `datetime.now(timezone.utc)` explicitly on insert.
  This phase has no password-update use case, so both fields are always equal at creation time.

`password_hasher.py`

- Wraps passlib bcrypt.
- Exposes `hash_password` and `verify_password`.

`jwt_handler.py`

- Uses python-jose.
- Creates HS256 JWT with `sub`, `iat`, `exp`.
- Decodes and returns `sub`.
- Raises jose errors for invalid or expired tokens.

`dependencies.py`

- Defines `get_current_user_id`.
- Uses `HTTPBearer(auto_error=False)` so missing token maps to `401`, not FastAPI default `403`.
- This dependency is HTTP adapter code. Other routers may use it, but application services should receive `current_user_id` as a plain string.

`router.py`

- Defines request/response schemas for register, login, me.
- Calls `build_auth_service(db)` from `flowpay.composition`.
- Maps `UsernameAlreadyExistsError` to `409 username_already_exists`.
- Maps `InvalidCredentialsError` to `401 invalid_credentials`.
- Must not import `users.adapters.*`.

### `flowpay.composition`

Builds concrete services:

- `UserService(SQLAlchemyUserRepository(db))`
- `SQLAlchemyCredentialsRepository(db)`
- `AuthService(credentials_repo, user_service, hash_password, verify_password)`

This is the allowed place for concrete cross-module adapter wiring.

## Database

Create tables from `docs/specs/05-persistence-model.md`:

- `users`
  - `id` text primary key
  - `username` text not null unique
  - `created_at` timestamptz not null
- `auth_credentials`
  - `user_id` text primary key references `users(id)`
  - `password_hash` text not null
  - `created_at` timestamptz not null
  - `updated_at` timestamptz not null

Generate the migration with Alembic autogenerate after ORM models are in place. Do not hand-write the migration file.

Expected autogenerate output:

- creates `users`;
- creates `auth_credentials`;
- adds unique constraint/index for `users.username`;
- adds foreign key from `auth_credentials.user_id` to `users.id`;
- downgrade drops `auth_credentials` before `users`.

Review the generated migration before applying it. Manual edits are allowed only to correct names/order/constraints generated by Alembic, not to bypass autogenerate.

## Endpoint Behavior

`POST /auth/register`

- Public.
- Creates user and credentials in one request transaction.
- Returns `201` with provisional `{ user }`.
- Duplicate username returns `409 username_already_exists`.
- Validation errors return `400 invalid_request`.
- Password is never returned.

`POST /auth/login`

- Public.
- Valid credentials return `200` with `access_token`, `token_type`, `expires_in`, and `user`.
- Invalid username or password returns `401 invalid_credentials`.

`GET /auth/me`

- Requires `Authorization: Bearer <token>`.
- Valid token returns `{ user }`.
- Missing, invalid, or expired token returns `401 unauthenticated`.

All errors use:

```json
{
  "error": {
    "code": "string",
    "message": "string"
  }
}
```

## Tests

### Unit Tests

`test_auth_service.py`

- register creates a user through `UserService` and stores a password hash.
- register duplicate raises `UsernameAlreadyExistsError`.
- login succeeds with correct password.
- login rejects wrong password.
- login rejects unknown user.
- service returns `UserSummary`, not repository records or credential records.

`test_password_hasher.py`

- hash is not plain text.
- correct password verifies.
- wrong password fails.

`test_jwt_handler.py`

- valid token round-trips user id.
- expired token raises — generate with a past `exp` directly:
  `exp = datetime.now(timezone.utc) - timedelta(seconds=1)`.
  No extra dependencies needed.
- malformed/tampered token raises.
- decoded token must come from `sub`.

No separate `UserService` unit test is required unless `UserService` gains logic beyond duplicate translation and record-to-summary mapping. Its behavior is covered through `AuthService` and integration tests.

### Integration Tests With PostgreSQL

- Register returns `201` and persists both user and credential rows.
- Stored password hash is not the submitted password.
- Duplicate register returns `409 username_already_exists`.
- Missing register fields return `400 invalid_request`.
- Login returns token with `expires_in = 3600`.
- Wrong password and unknown user return `401 invalid_credentials`.
- `/auth/me` returns authenticated user for valid token.
- `/auth/me` rejects missing, invalid, and expired tokens.
- Request transaction commits on success.
- Request transaction rolls back if credential creation fails after user creation.

### Architecture Boundary Tests

Add lightweight static tests using Python `ast` or import scanning:

- `flowpay.auth` must not import `flowpay.users.adapters`.
- `flowpay.auth` must not import users ORM modules.
- `flowpay.auth.application` must not import FastAPI, SQLAlchemy, passlib, or jose.
- `flowpay.users.application` must not import FastAPI or SQLAlchemy.
- `flowpay.*.adapters.*repository*` must not call `.commit()` or `.rollback()`.
- `flowpay.composition` is allowed to import concrete adapters from multiple modules.

These tests are the safety net that lets the implementation stay simple without silently drifting into a tangled monolith.

## Success Criteria

- Implementation does not create domain data classes with no behavior.
- Auth and users modules preserve ADR 0001 dependency direction.
- `auth` imports only `users.application.*`, never `users.adapters.*` or users ORM models.
- `flowpay.composition` is the only place wiring concrete repositories across modules.
- `POST /auth/register` is explicitly provisional and returns `{ user }`.
- User and credential creation are atomic under the request unit of work.
- Passwords are hashed and never returned.
- JWT payload contains only `sub`, `iat`, and `exp`.
- Alembic migration is generated with autogenerate and reviewed before applying.
- Auth endpoint tests pass against PostgreSQL.
- Architecture boundary tests pass.
