# FlowPay Backend - Wallets Module

## Goal

Implement the `wallets` backend module: wallet creation and retrieval.

This module owns wallet identity, user-wallet relationship, and wallet existence. It does not create transactions, record balances, or process transfers. **No HTTP endpoints yet.** Wallets module is the foundation for ledger and transfers integration.

## TL;DR

- Build a lightweight `wallets` backend module with wallet creation and lookup.
- Each user has exactly one wallet in Colombian pesos (COP).
- Keep the implementation simple: no domain logic yet, just persistence and identity.
- **No HTTP endpoints.** Wallets service is called by composition layer (e.g., from register later).
- Preserve architecture through import boundaries, ports, composition root, and architecture tests.
- Use PostgreSQL-backed integration tests for persistence and logic.

## Team TL;DR

**What we're building**: A wallet persistence layer that stores wallet identity and ownership. The wallet is the container for future money movement, balance, and transaction history.

**Why it matters**: Wallets are the foundation for ledger (which records transactions) and transfers (which move money). This module enables the financial core.

**Timeline impact**: Standalone module, 1 day. No blocking integrations yet. Sets up the foundation for ledger work.

## Design Principle

Use the same light hexagonal structure as the `users` module.

Wallets are simple: create one per user, retrieve by ID or user ID. This phase has only lightweight persistence invariants: one wallet per user, fixed `COP` currency, and a wallet row that later becomes the transfer locking boundary. No complex financial domain logic yet. Keep the implementation minimal without premature abstraction.

Use:

- `application/` for use cases and public DTOs;
- `ports/` for repository contracts and adapter-neutral records;
- `adapters/` for SQLAlchemy ORM and persistence.

## Contract Scope

**This phase: No HTTP endpoints.**

Wallets module provides:

- `WalletService.create_wallet(user_id: str) -> WalletSummary`
- `WalletService.get_by_id(wallet_id: str) -> WalletSummary | None`
- `WalletService.get_by_user_id(user_id: str) -> WalletSummary | None`

These are called by composition layer or future integration (e.g., `POST /auth/register` will eventually call `create_wallet`).

**Future integration** (not this phase):
- `POST /auth/register` will create user + wallet + welcome bonus in one request.
- `GET /wallet` endpoint will retrieve authenticated user's wallet.
- For now, these are out of scope.

## Architecture Constraints

Follow ADR 0001:

- Keep `wallets` as a separate module.
- Keep application code independent from FastAPI and SQLAlchemy.
- `wallets` may read from `users` public API only.
- `wallets` must not import `users.adapters.*` or users ORM models.
- Concrete cross-module wiring belongs in `flowpay/composition.py`.
- Repositories use `flush()` but do not `commit()` or `rollback()`.
- The request DB session is the unit of work: `commit()` after successful request.

## Module Details

### `wallets.application.wallet_service`

Define:

- `WalletSummary`: public DTO with `id`, `user_id`, `currency`, `created_at`.
- `WalletService`.

Responsibilities:

- `create_wallet(user_id: str) -> WalletSummary`
- `get_by_id(wallet_id: str) -> WalletSummary | None`
- `get_by_user_id(user_id: str) -> WalletSummary | None`
- Generate wallet IDs with `generate_id("wal_")`, matching the existing `users` module pattern where the application service creates the resource identity.
- Convert repository records to `WalletSummary`.

This file is the public API other modules may call.

### `wallets.ports.wallet_repository`

Define:

- `WalletRecord`: adapter-neutral persistence record with `id`, `user_id`, `currency`, `created_at`.
- `WalletRepository` protocol.

Rationale:

- Gives application code a stable record shape without importing SQLAlchemy.
- Avoids ORM leakage into application code.

### `wallets.adapters`

**`wallet_orm.py`**

- SQLAlchemy model for `wallets`.
- Owns table mapping only.
- Fixed currency: `COP`.

**`wallet_repository.py`**

- Implements `WalletRepository`.
- Accepts the wallet ID from `WalletService`.
- Uses `flush()` after insert.
- Never calls `commit()` or `rollback()`.

ID generation note:

- The existing `users` module generates user IDs in `UserService`.
- Keep `wallets` aligned with that convention: `WalletService.create_wallet()` generates `wallet_id = generate_id("wal_")`, then calls the repository with the generated ID.
- Repositories persist records and translate database errors; they do not own resource identity creation.

## Database

Create table from `docs/specs/05-persistence-model.md`:

- `wallets`
  - `id` text primary key
  - `user_id` text not null unique
  - `currency` text not null, fixed to `COP`
  - `created_at` timestamptz not null
  - foreign key on `user_id` references `users(id)`

Generate the migration with Alembic autogenerate after the ORM model is in place and `backend/migrations/env.py` imports `flowpay.wallets.adapters.wallet_orm`. Do not hand-write the migration file.
