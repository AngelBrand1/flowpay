# NFC Module — Implementation and Fixes

## Overview

Complete implementation of the NFC module for FlowPay Mobile. The module allows two Android devices to exchange a transfer recipient by bringing the phones close together, using HCE (Host Card Emulation) as the broadcast channel and ISO-DEP as the scanning channel. NFC is solely a recipient resolution mechanism — it does not execute or authorize transfers.

## Backend Scope

NFC did not require a dedicated backend module, endpoint, migration, or service.

**Why:** NFC is an input channel, not a money-moving operation. Its only job is to resolve a recipient username from a physical NFC handshake and pre-fill the transfer form. Once the user confirms the amount, the app calls the existing `POST /transfers` endpoint with `destination_username` — the same endpoint used by the manual flow (see plan `11-transfer-feature-backend.md`). The backend resolves the username to a wallet internally, as it would for any transfer.

No NFC-specific data is persisted. No new error codes, domain models, or ledger entries were introduced for NFC. The backend never knows — or needs to know — that a username came from NFC rather than from the keyboard.

This is a deliberate boundary: NFC lives entirely in the mobile adapter layer and the backend remains a general-purpose transfer authority.

## Architecture

The module implements two symmetrical roles on the same device:

### Sender Role (HCE — Host Card Emulation)

When the user is authenticated, the phone passively announces itself as a payment recipient. It requires no user action.

```
NfcPresenceProvider
  ├── useEffect([], [])  →  initNfcManager()   [once on mount]
  └── useEffect([accessToken, username])
        ├── authenticated   →  FlowPayHce.setPayload({ type, username })
        └── no session      →  FlowPayHce.clearPayload()
```

The `FlowPayHce` native module (generated by the Expo plugin) exposes three methods to JS:
- `isSupported()` — verifies that the hardware supports HCE
- `setPayload(json)` — writes the payload to `FlowPayHcePayloadStore` (Kotlin `@Volatile` singleton)
- `clearPayload()` — clears the payload

When another phone sends a SELECT APDU with the AID `F0464C4F57504159` (`F0FLOWPAY`), `FlowPayHostApduService` responds with the JSON payload + `0x9000 OK`.

### Scanner Role (ISO-DEP)

The phone initiating the transfer requests `IsoDep` technology, sends the SELECT APDU, and decodes the response.

```
useNfcRecipientScanner
  └── scanHceRecipientPayload(timeoutMs)
        ├── NfcManager.requestTechnology(IsoDep)
        ├── isoDepHandler.transceive(SELECT_APDU)
        ├── validates STATUS_OK [0x90, 0x00]
        └── decodeRecipientPayloadFromText(bytes → string → JSON)
```

### Full Flow

```
Phone B (receiver, HCE sender)           Phone A (payer, scanner)
─────────────────────────────────        ──────────────────────────────
NfcPresenceProvider mounts               TransferScreen mounts
  → FlowPayHce.setPayload(JSON)            → scanContinuously() loop

User brings phones together
  ← SELECT APDU (AID F0FLOWPAY) ──────────────────────────────────────
  → JSON payload + 0x9000 ────────────────────────────────────────────
                                         decodeRecipientPayloadFromText
                                         setRecipient(username)
                                         setStep('amount')
```

## Parsing Layer — `nfcPayload.ts`

Three entry points for different data sources:

| Function | Input | Usage |
|---|---|---|
| `decodeRecipientPayloadFromText` | JSON string | HCE response bytes → string |
| `decodeRecipientPayloadFromRecord` | `NdefRecord` | Passive NDEF tags |
| `decodeRecipientPayloadFromTag` | `TagEvent` | Full scan events |
| `encodeRecipientPayload` | `NfcRecipientPayload` | Generates `NdefRecord` for tests |

Applied validations:
- `type === 'flowpay_recipient'` — rejects payloads from other apps
- `username` is a non-empty string after trim
- Invalid JSON → `NfcPayloadError('invalid_json')`
- Incorrect object shape → `NfcPayloadError('invalid_shape')`
- Record without text payload → `NfcPayloadError('missing_payload')`

The AID `F0464C4F57504159` is in the `F0xxxxxxxxxxxxxxxx` range reserved for proprietary applications (ISO 7816-4 §8.2.1.2), which avoids collisions with other systems.

## Applied Fixes

### 1. `NfcManager.start()` called on every scan

**Problem:** `scanHceRecipientPayload` called `NfcManager.start()` at the beginning of each attempt. In `scanContinuously`, this happened every 2.5 seconds.

**Fix:** `initNfcManager()` was extracted as a public function. It is called only once from `NfcPresenceProvider` on mount (`useEffect([], [])`). `scanHceRecipientPayload` no longer has initialization side effects.

```ts
// hceAdapter.ts
export async function initNfcManager(): Promise<void> {
  await NfcManager.start()
}
```

```tsx
// NfcPresenceProvider.tsx
useEffect(() => {
  initNfcManager().catch(() => {})
}, [])
```

---

### 2. Infinite loop on permanent NFC error

**Problem:** The `catch` in `scanContinuously` swallowed any error and continued the loop. If NFC was disabled or permission was denied, the loop ran until the component unmounted.

**Fix:** The loop only continues if the error is `flowpay_hce_scan_timeout` (expected timeout). Any other error sets `status = 'unavailable'` and terminates the loop.

```ts
} catch (error) {
  if (error instanceof Error && error.message === 'flowpay_hce_scan_timeout') {
    continue
  }
  setStatus('unavailable')
  return
}
```

---

### 3. Redundant `try/catch` in `decodeRecipientPayloadFromRecord`

**Problem:** The final block of the method had `if (e instanceof NfcPayloadError) throw e; throw e` — both branches re-threw identically.

**Fix:** The block was removed, leaving only the direct call:

```ts
return decodeRecipientPayloadFromText(decoded)
```

---

### 4. `unavailable` state without UI representation

**Problem:** The ternary in `TransferScreen` had only three cases: `scanning`, `found`, and "everything else". The `unavailable` state showed "NFC active".

**Fix:**

```tsx
{nfcScanStatus === 'scanning'
  ? 'Reading via NFC'
  : nfcScanStatus === 'found'
    ? 'NFC detected'
    : nfcScanStatus === 'unavailable'
      ? 'NFC unavailable'
      : 'NFC active'}
```

---

### 5. Idempotency key with insecure fallback

**Problem:** The fallback used `Math.random()` to generate the transfer's idempotency key.

**Fix:** Replaced with a standard UUID v4. It uses `globalThis.crypto.randomUUID()` when available (modern Hermes), with a UUID v4 fallback via `Math.random()` when `globalThis.crypto` is `undefined`.

```ts
function createIdempotencyKey(): string {
  if (globalThis.crypto?.randomUUID) {
    return globalThis.crypto.randomUUID()
  }
  return 'xxxxxxxx-xxxx-4xxx-yxxx-xxxxxxxxxxxx'.replace(/[xy]/g, (c) => {
    const r = (Math.random() * 16) | 0
    return (c === 'x' ? r : (r & 0x3) | 0x8).toString(16)
  })
}
```

The UUID v4 format produces 122 bits of entropy, enough to make collisions practically impossible in financial operations.

## Respected Design Guardrails

- **NFC does not move money.** It only resolves a candidate username. The user must enter an amount and explicitly confirm.
- **Manual fallback always available.** If NFC fails, is not available, or the user types directly, the flow continues without NFC.
- **The screen does not touch the NFC library.** `TransferScreen` imports `useNfcRecipientScanner` — never `react-native-nfc-manager` directly.
- **HCE is opportunistic.** Errors in `startHceRecipient` or `initNfcManager` are silently ignored; the app works without NFC.
- **Tokens are not passed via NFC.** The payload only contains `{ type, username }` — no credentials or financial information.

## Known Technical Debt

**`initNfcManager` lives in the presence provider.** `NfcPresenceProvider` manages HCE (broadcast), but `NfcManager.start()` is also necessary for the scanner. It works today because the provider wraps the entire app. If a second scanning context is added in the future or independent lifecycle control is needed, extract to a dedicated `NfcManagerProvider`.

## Team TL;DR

**What was built:** Users can bring two Android phones close together to have the transfer recipient auto-fill, without having to type the username manually.

**Why it matters:** It reduces friction in the most common payment flow — transferring to someone physically present — and differentiates the product from text-only transfers.

**Impact:** The functionality is complete and stable. The manual flow remains available as a fallback on devices without NFC or when the user prefers to type the recipient.
